# Revit AI Agent 项目方案

面向 Revit 使用者、BIM 团队、插件开发者和公司内部自动化团队。

本文档目标是从 0 开始，规划一套基于 Codex、Claude Code、Antigravity、MCP、pyRevit、Revit API 的公司级 Revit AI Agent 工作流。它的目标不是让 AI “一键解决所有 Revit 问题”，而是把 AI 变成一个可靠的 Revit 开发和生产助手：能理解你的模型、理解你的操作习惯、帮你写代码、开发插件、检查问题、批量处理图纸和数据，并在关键操作前保留人工确认。

## 1. 项目愿景

我们希望打造一个“懂公司标准、懂项目习惯、懂 Revit API、能和人协作”的 AI Agent。

它应该能帮助完成这些事情：

- 编写 pyRevit 脚本。
- 编写 C# Revit 插件。
- 查询和解释 Revit API。
- 根据当前模型状态生成可执行方案。
- 批量处理图纸、视图、族、房间、门窗、明细表、参数。
- 检查模型问题，例如命名、参数缺失、视图设置、图纸完整性。
- 生成插件按钮、工具栏、部署脚本和使用说明。
- 记录你的常用操作习惯，并在后续任务中自动参考。
- 帮助团队统一插件开发、测试、发布和维护方式。

它不应该直接无确认地做这些事：

- 删除模型元素。
- 大批量修改模型参数。
- 改动中心文件或云模型。
- 执行 AI 生成但未经检查的代码。
- 自动提交、发布或覆盖团队插件。

正确的目标是：**AI 负责提案、生成、检查和执行可回滚任务，人负责确认关键决策。**

## 2. 适用人员

### Revit 使用者

不需要懂太多编程，只需要会描述问题、选择模型元素、看懂 AI 给出的操作计划。

典型需求：

- “帮我把所有门按楼层编号。”
- “检查图纸里哪些视图没有放到图纸上。”
- “把房间面积导出成 Excel。”
- “帮我做一个 pyRevit 按钮。”

### BIM 负责人

重点关注标准化、批量检查、团队部署和质量控制。

典型需求：

- “所有项目都要检查共享参数。”
- “导出模型健康报告。”
- “插件必须按公司版本发布。”
- “记录每次批处理影响了哪些元素。”

### 插件开发者

重点关注 Revit API、C#、pyRevit、MCP、测试和发布。

典型需求：

- “根据这个需求生成 ExternalCommand。”
- “把 pyRevit 原型改成 C# 插件。”
- “兼容 Revit 2022、2024、2025、2027。”
- “给插件增加日志、配置文件和错误处理。”

## 3. 推荐工具栈

### AI 编码平台

#### Codex

适合直接在项目代码仓库里工作。可以读文件、改代码、运行测试、写文档、协助重构和排查问题。适合做“项目开发主力”。

建议用途：

- 管理插件源码。
- 编写 pyRevit 工具。
- 编写 C# 插件项目。
- 维护 MCP 服务。
- 生成团队文档。
- 做代码审查和测试修复。

#### Claude Code

适合长上下文推理、复杂需求拆解、解释代码、生成方案。适合做“架构顾问”和“复杂任务拆解助手”。

建议用途：

- 讨论插件架构。
- 拆解复杂 Revit 自动化需求。
- 审查 AI Agent 的提示词和安全规则。
- 生成复杂业务逻辑草稿。

#### Antigravity

适合多 Agent、IDE 化开发、项目导航和快速原型。适合做“交互式开发环境”和“多模型协作平台”。

建议用途：

- 让不同 Agent 分别负责文档、代码、测试、UI。
- 快速试验 Revit 工具原型。
- 辅助团队成员进入同一项目。

建议策略：不要强行统一所有同事只用一个平台。公司可以统一底层代码仓库、文档、MCP 协议和安全规则，前端 AI 平台可以多样化。

### Revit 自动化工具

#### pyRevit

最适合快速开发 Revit 小工具。对 Revit 使用者友好，迭代快，适合内部效率工具。

适合：

- 批量参数处理。
- 视图和图纸整理。
- 明细表导入导出。
- 快速模型检查。
- 团队内部工具栏。

#### C# Revit 插件

适合正式产品化、复杂 UI、高性能和长期维护。

适合：

- 大型插件。
- 商业级工具。
- 多版本发布。
- 复杂交互界面。
- 与公司系统集成。

#### Dynamo

适合可视化原型和非开发人员参与。很多逻辑可以先用 Dynamo 验证，再交给 AI 改写成 pyRevit 或 C#。

#### RevitLookup

Revit API 开发必备工具。它可以查看模型元素的真实 API 属性、参数、类型和几何信息。AI 写 Revit 代码之前，最好先用 RevitLookup 查一下目标元素。

### 数据和协作工具

#### Git

所有插件、脚本、MCP、文档都应进入 Git 仓库。

建议分支：

- `main`：稳定版本。
- `dev`：内部测试版本。
- `feature/*`：单个功能开发。
- `release/revit-2025`：按 Revit 版本维护发布分支。

#### SQLite / DuckDB

适合存放模型快照、参数表、检查结果、用户操作记录。

#### Excel

适合和普通 Revit 用户交互。很多批处理可以设计为“导出 Excel -> 人工检查 -> 导入执行”。

#### Speckle / IFC / APS

适合跨软件数据交换、Web 可视化、模型版本和数据分析。不是第一阶段必须，但中后期很有价值。

## 4. 整体架构

推荐架构分为 6 层。

### 第 1 层：AI 平台层

包括 Codex、Claude Code、Antigravity。

职责：

- 理解自然语言需求。
- 生成代码。
- 解释错误。
- 修改项目文件。
- 生成测试和文档。
- 调用 MCP 工具。

### 第 2 层：知识层

包括 Revit API 文档、公司标准、历史插件、常见问题、用户习惯。

内容：

- Revit API Docs。
- Autodesk 官方文档。
- Revit SDK 示例。
- 公司 BIM 标准。
- 公司命名规则。
- 图纸标准。
- 参数标准。
- 族库规范。
- 过往项目问题。
- 常用 pyRevit 脚本。

### 第 3 层：MCP 工具层

MCP 是 AI 和外部工具之间的标准接口。可以把 Revit、文档库、数据库、文件系统、任务系统都封装成 AI 可调用的工具。

建议优先做这些 MCP：

- `revit_context_mcp`：读取当前 Revit 状态。
- `revit_docs_mcp`：查询 Revit API 文档。
- `company_standards_mcp`：查询公司 BIM 标准。
- `model_snapshot_mcp`：读取模型快照数据库。
- `pyrevit_tools_mcp`：生成和部署 pyRevit 工具。
- `task_memory_mcp`：记录用户偏好和操作习惯。

### 第 4 层：Revit 执行层

包括 pyRevit、C# 插件、ExternalEvent、Revit API。

职责：

- 在 Revit 主线程执行 API。
- 读取当前文档。
- 读取选择集。
- 创建事务。
- 修改模型。
- 导出日志。
- 执行失败时回滚。

### 第 5 层：安全和审计层

所有模型修改都应经过安全控制。

必须有：

- dry-run 预演模式。
- 修改前显示影响范围。
- 修改后输出日志。
- 支持 Transaction 回滚。
- 高风险操作必须人工确认。
- 禁止 AI 直接删除大量元素。
- 禁止 AI 直接修改中心文件而不提示。

### 第 6 层：团队发布层

包括插件打包、版本管理、部署脚本、用户说明。

职责：

- 按 Revit 版本发布插件。
- 管理 pyRevit extension。
- 管理 `.addin` 文件。
- 记录变更日志。
- 给用户提供一键更新。
- 收集错误报告。

## 6. Agent 能力设计

### 能力 1：写代码

用户输入：

```text
帮我写一个 pyRevit 按钮，选择当前视图里的所有门，检查是否缺少“门编号”参数。
```

Agent 应该做：

1. 查询公司参数标准。
2. 查询 Revit API 示例。
3. 生成 pyRevit 脚本。
4. 给出按钮目录结构。
5. 增加错误提示。
6. 生成使用说明。

### 能力 2：开发正式插件

用户输入：

```text
把这个 pyRevit 工具改成支持 Revit 2024 和 2025 的 C# 插件。
```

Agent 应该做：

1. 判断 API 版本差异。
2. 生成项目结构。
3. 创建 ExternalCommand。
4. 添加 `.addin` 模板。
5. 添加日志和异常处理。
6. 生成打包脚本。

### 能力 3：理解当前模型

用户输入：

```text
分析当前模型里哪些房间没有编号。
```

Agent 不应该凭空回答。它应该通过 MCP 或 pyRevit 工具获取当前模型数据。

建议流程：

1. Revit 插件导出房间表。
2. MCP 把房间表提供给 AI。
3. AI 分析缺失项。
4. AI 生成报告。
5. 用户确认是否批量修复。

### 能力 4：记住用户习惯

Agent 可以记录这些偏好：

- 用户常用 Revit 版本。
- 用户常用语言：中文。
- 用户偏好先用 pyRevit 原型，再做 C# 插件。
- 用户常用参数名。
- 用户常用图纸命名规则。
- 用户常做的批处理任务。
- 用户希望输出 Excel 报告还是 Revit 弹窗。

但不应记录：

- 密码。
- 授权码。
- 商业敏感合同信息。
- 未经允许的个人隐私。
- 客户机密模型内容。

建议把“用户习惯”存成可查看、可编辑、可删除的 Markdown 或 JSON 文件。

示例：

```json
{
  "user": "Yang",
  "language": "zh-CN",
  "common_revit_versions": ["2022", "2024", "2025", "2027"],
  "preferred_workflow": "先用 pyRevit 快速验证，再转 C# 插件",
  "report_format": "Excel + Markdown",
  "safety_preference": "所有批量修改先 dry-run"
}
```

### 能力 5：解决日常 Revit 问题

可以优先覆盖这些高频场景：

- 批量重命名视图。
- 批量创建图纸。
- 检查未上图视图。
- 检查房间编号和名称。
- 检查门窗编号。
- 导出门窗表。
- 批量写入共享参数。
- 检查族命名。
- 检查视图样板。
- 检查图纸标题栏参数。
- 统计模型元素数量。
- 清理未使用视图。
- 生成模型健康报告。

## 7. MCP 设计建议

### revit_context_mcp

目标：让 AI 获取当前 Revit 上下文。

可提供工具：

- `get_active_document_info`
- `get_active_view_info`
- `get_selection`
- `get_selected_elements_parameters`
- `get_categories_summary`
- `export_rooms`
- `export_sheets`
- `export_views`
- `export_family_instances`

注意：第一阶段只读，不要直接修改模型。

### revit_action_mcp

目标：让 AI 发起受控 Revit 操作。

可提供工具：

- `preview_parameter_update`
- `apply_parameter_update`
- `preview_view_rename`
- `apply_view_rename`
- `create_sheets_from_excel`
- `run_pyrevit_script`

要求：

- 所有 `apply_*` 工具必须有人确认。
- 所有操作必须写日志。
- 所有操作必须支持事务失败回滚。

### revit_docs_mcp

目标：让 AI 查询 Revit API 文档。

可索引：

- Autodesk Revit API Developer Guide。
- RevitAPIDocs。
- Revit SDK Samples。
- 公司已有插件代码。
- 公司常用 API 封装。

### company_standards_mcp

目标：让 AI 了解公司标准。

可索引：

- 图纸命名标准。
- 视图命名标准。
- 族命名标准。
- 参数标准。
- 出图标准。
- 模型检查标准。

## 8. 安全规则

必须明确告诉所有 Agent：

1. 不允许在没有用户确认时删除 Revit 元素。
2. 不允许在没有用户确认时批量修改参数。
3. 不允许直接操作中心文件。
4. 不允许执行来源不明的脚本。
5. 不允许把客户模型数据发送到未经批准的外部服务。
6. 所有批量操作必须先显示影响数量。
7. 所有模型修改必须使用 Transaction。
8. 所有失败必须回滚并输出错误日志。
9. 所有正式插件必须区分 Revit 版本。
10. 所有 AI 生成代码必须经过测试模型验证。

建议默认执行流程：

```text
用户提出需求
  -> Agent 理解需求
  -> Agent 读取模型上下文
  -> Agent 生成操作计划
  -> 用户确认
  -> dry-run
  -> 用户二次确认
  -> 执行 Transaction
  -> 输出日志和报告
```

## 9. Revit 多版本策略

你常用 Revit 2022、2024、2025、2027，需要特别注意版本差异。

建议策略：

- Revit 2022 和 2024：优先使用 pyRevit 和 .NET Framework 插件。
- Revit 2025：注意 .NET 8 迁移。
- Revit 2027：单独维护兼容层，不要默认假设旧插件能直接运行。
- 公共逻辑尽量放到独立库里。
- Revit API 调用放到版本适配层。
- 发布包按 Revit 版本拆分。

建议命名：

```text
CompanyTools.Revit2022
CompanyTools.Revit2024
CompanyTools.Revit2025
CompanyTools.Revit2027
CompanyTools.Common
```

## 10. 团队工作流

### 普通用户提需求

模板：

```text
我要解决的问题：
当前手工做法：
希望自动化后的效果：
涉及的 Revit 版本：
是否会修改模型：
是否需要导出 Excel：
能否提供测试模型：
```

### AI 生成方案

Agent 输出：

- 需求理解。
- 风险判断。
- 需要读取哪些模型信息。
- 是否适合 pyRevit。
- 是否需要 C# 插件。
- 操作步骤。
- 预期结果。

### 开发者实现

开发者使用 Codex 或 Claude Code：

1. 读取需求文档。
2. 创建功能分支。
3. 生成代码。
4. 在测试模型验证。
5. 写变更日志。
6. 提交 Pull Request。

### BIM 负责人验收

验收内容：

- 是否符合公司标准。
- 是否有误改模型风险。
- 是否有 dry-run。
- 是否有日志。
- 是否有使用说明。
- 是否在目标 Revit 版本测试通过。

## 11. 第一期 MVP

第一期不要追求“解决一切问题”。建议做一个可落地的最小版本。

### MVP 目标

做一个只读为主、少量受控修改的 Revit AI 助手。

包含：

- pyRevit 工具栏。
- 模型信息导出。
- AI 读取导出的模型数据。
- AI 生成检查报告。
- AI 生成 pyRevit 脚本。
- 人工确认后运行脚本。

### MVP 功能

1. 导出当前模型基本信息。
2. 导出房间表。
3. 导出门窗表。
4. 导出视图和图纸列表。
5. 检查缺失参数。
6. 生成 Markdown/Excel 报告。
7. 根据检查结果生成修复脚本。
8. 所有修复先 dry-run。

### MVP 不做

- 不直接连接中心文件自动修改。
- 不自动删除元素。
- 不做复杂 UI。
- 不做公司全员部署。
- 不做所有 Revit 版本一次性完美兼容。

## 12. 第二期能力

第二期可以加入：

- MCP 直接读取 Revit 当前上下文。
- 公司标准知识库。
- 用户习惯记忆。
- 插件自动生成模板。
- C# 插件多版本构建。
- 错误日志收集。
- 内部工具市场。
- 任务历史记录。

## 13. 第三期能力

第三期可以加入：

- Revit 内嵌聊天面板。
- 多 Agent 协作。
- 自动生成测试模型。
- 自动对比修改前后模型数据。
- 与 Speckle、APS、Power BI 集成。
- 公司级 BIM 问题知识库。
- 项目级 Agent，按项目记住特殊标准。

## 14. 推荐的 Agent 角色

### 需求分析 Agent

负责把用户自然语言变成清晰任务。

### Revit API Agent

负责查 API、写代码、解释 Revit 限制。

### pyRevit Agent

负责快速生成内部工具。

### C# 插件 Agent

负责正式插件、UI、部署、多版本兼容。

### BIM 标准 Agent

负责检查公司标准、项目标准、图纸规范。

### 测试 Agent

负责生成测试数据、测试步骤、检查日志。

### 发布 Agent

负责打包、版本号、变更日志、发布说明。

## 15. 推荐提示词模板

### 写 pyRevit 工具

```text
你是公司内部 Revit/pyRevit 开发助手。
请根据以下需求生成 pyRevit 工具。
要求：
1. 先说明你理解的需求。
2. 说明是否会修改模型。
3. 所有修改必须放在 Transaction 中。
4. 批量修改前必须输出影响元素数量。
5. 生成完整目录结构和 script.py。
6. 输出使用说明。

需求：
{用户需求}
```

### 写 C# 插件

```text
你是 Revit C# 插件开发助手。
目标 Revit 版本：{版本}
请生成 ExternalCommand 插件代码。
要求：
1. 使用清晰的事务控制。
2. 处理异常并返回 Result.Failed。
3. 不要硬编码不稳定路径。
4. 说明需要引用的 Revit API DLL。
5. 给出 .addin 示例。
6. 说明测试步骤。

需求：
{用户需求}
```

### 检查 AI 生成代码

```text
请以 Revit API 代码审查员身份检查以下代码。
```

## 16. 数据和记忆设计

建议分三类记忆。

### 用户偏好记忆

例如：

- 常用 Revit 版本。
- 偏好的输出格式。
- 常用插件目录。
- 常用参数名。
- 喜欢中文说明。

### 项目记忆

例如：

- 项目编号。
- 项目使用的 Revit 版本。
- 项目特殊参数。
- 项目图纸规则。
- 项目族命名规则。

### 公司标准记忆

例如：

- 统一图纸标准。
- 统一参数标准。
- 统一族库标准。
- 插件发布规范。

所有记忆都应该可查看、可编辑、可删除。

## 18. 开发路线图

### 第 1 周：准备阶段

- 建 Git 仓库。
- 收集公司标准。
- 收集常用 Revit 问题。
- 安装 RevitLookup。
- 整理 pyRevit 工具目录。
- 确定测试模型。

### 第 2 周：MVP 原型

- 创建 pyRevit 工具栏。
- 实现模型数据导出。
- 实现房间/门窗/视图/图纸导出。
- 让 Codex 或 Claude Code 读取导出数据生成报告。

### 第 3 周：AI 生成工具

- 建立提示词模板。
- 让 AI 生成 3 个 pyRevit 小工具。
- 开发者审查并修复。
- 在测试模型验证。

### 第 4 周：安全和发布

- 加 dry-run。
- 加日志。
- 加错误处理。
- 写用户说明。
- 小范围给 2 到 3 位同事试用。

### 第 2 个月：MCP 和记忆

- 开发只读 Revit Context MCP。
- 建公司标准知识库。
- 加用户偏好文件。
- 支持 Agent 根据标准回答问题。

### 第 3 个月：正式插件化

- 选择高价值工具转 C# 插件。
- 建多版本项目模板。
- 做 Revit 2025/.NET 8 兼容验证。
- 建发布流程。

## 19. 成功标准

第一阶段成功标准：

- 至少 5 个高频 Revit 任务可以由 AI 辅助完成。
- 至少 3 个 pyRevit 工具通过测试模型验证。
- AI 能根据公司标准生成检查报告。
- 所有批量修改都有 dry-run 和日志。
- 普通 Revit 用户能按文档提交自动化需求。

中期成功标准：

- 团队能稳定维护 pyRevit 工具库。
- 开发者能用 Codex/Claude Code 快速生成插件。
- BIM 负责人能查看执行日志。
- 用户习惯和项目标准能被 Agent 正确引用。

长期成功标准：

- 公司形成自己的 Revit 自动化知识库。
- 常见问题优先由 Agent 给出解决方案。
- 插件开发周期明显缩短。
- 团队标准执行更加稳定。

## 20. 风险和应对

### 风险 1：AI 生成错误 Revit API 代码

应对：

- 必须查文档。
- 必须用测试模型。
- 必须代码审查。
- 必须日志和回滚。

### 风险 2：误改真实项目模型

应对：

- 默认 dry-run。
- 高风险操作二次确认。
- 禁止直接操作中心文件。
- 先在复制模型测试。

### 风险 3：团队平台太多，流程混乱

应对：

- 平台可以多样，仓库和规范必须统一。
- 所有工具进入同一 Git 仓库。
- 所有提示词和标准集中管理。

### 风险 4：公司标准不清晰

应对：

- 先整理标准文档。
- 没有标准就让 Agent 先提出候选标准。
- BIM 负责人确认后固化。

### 风险 5：Revit 版本兼容复杂

应对：

- 按版本分支或分包。
- 不承诺一次支持所有版本。
- 先支持当前项目最常用版本。

## 22. 最小可执行起步方案

如果今天就要开始，建议这样做：

1. 用 Codex 创建项目仓库和文档。
2. 用 pyRevit 做一个 `AI Tools` 工具栏。
3. 第一个按钮只负责导出模型数据，不修改模型。
4. 把导出的 JSON/Excel 交给 Codex 或 Claude 分析。
5. 让 AI 生成检查报告。
6. 从报告里挑一个低风险问题，让 AI 生成修复脚本。
7. 人工审查脚本。
8. 在测试模型运行。
9. 记录日志。
10. 再决定是否扩展到真实项目。

## 23. 核心原则

这套系统最重要的原则：

- AI 可以很聪明，但 Revit 模型必须安全。
- 先只读，再 dry-run，再小范围修改。
- 先 pyRevit 快速验证，再 C# 插件产品化。
- 平台可以多，但代码仓库、标准和日志必须统一。
- 用户习惯可以记住，但必须可查看、可编辑、可删除。
- 不追求一口吃成万能 Agent，先解决高频、低风险、可验证的问题。

最终目标不是替代 Revit 使用者，而是给每个 Revit 使用者配一个懂公司标准、懂模型数据、懂插件开发的助手。
